**A BAI2 statement names its two parties the way a real BAI2 file does, and
signs its balances** (#57, part b). Two things a consumer of the file will see
change.

The `02` group header gave `ultimate receiver` as the account's *name* and
`originator` as its id - both the customer, with the bank named nowhere - so
every statement claimed the account had originated its own statement.
`moov-io/bai2`'s `sample1.txt`, now vendored as
`tests/samples/external/bai2-sample1.txt`, settles the direction: its `01` is
`sender=0004, receiver=12345` and its `02` is
`ultimate receiver=12345, originator=0004`, the same party first in one and
second in the other. **In BAI2 the originator of a group is the bank that
produced the file**, which reads oddly beside ISO 20022, where an originator is
whoever started a payment. The two parties are derived once now and handed to
both records, so they cannot drift apart again.

**Balances and control totals carry an explicit sign.** They were written with a
`-` when negative and nothing when positive. The sample puts `+` on all four of
its control totals and both `03` balances, and no sign at all on any movement
amount - the same line this module already drew between a balance and a movement,
so only the notation changed: `49,+25125000,5/` where it said `49,25125000,5/`.
Not adopted is that file's zero-padding to a fixed width, which a
comma-delimited format does not need and which it applies at three different
widths in one file.

That outside file is the first real BAI2 the mock has been shown, and it also
**confirmed two readings the module had flagged as guesses** - record counts
include the trailer that states them, counting `88` continuations among them, and
control totals are signed, a `98` summing its accounts and a `99` its groups -
and confirmed that the `03` names an account number rather than an IBAN.
`tests/test_bai2_external.py` recomputes each of those with its own parser, so
nothing asks `mockbank.bai2` whether `mockbank.bai2` is right.

It **corrected the reason** recorded for keeping movement totals off the `03`.
The reason given was that a summary would be counted twice, once in the summary
and again in each `16`. That is exactly what BAI2 does: each `49` in the sample is
precisely twice the sum of its own `16`s. Balances-only is still what the mock
writes, but as a choice rather than as an avoidance of a problem that was not
there.

It could **not** settle the two placeholder transaction codes, which stay marked
in `PLACEHOLDER_CODES` rather than being promoted because the issue closed:
nothing in the file is an outgoing customer transfer or one coming back, and the
one public repository carrying the full BAI code list has no licence at all.

And it showed that **`mockbank.bai2.read` cannot read a real BAI2 file**, in
three ways: an undeclared `88`, and a value-dated funds type occupying three
fields where the declaration allows one - in the `16`, where it is refused, and
in the summary group, where it escapes as a bare `ValueError` rather than as a
refusal. That is #114, and each way is pinned by a passing test so that none of
them can be half-fixed or quietly rot. Nothing a user of the mock does reaches
`read`; it matters because a reader that has never opened a file it did not write
only ever agrees with itself.

One consequence worth naming, because it is where the tests moved: the account's
name reached no record once the `02` was fixed, so the four separator tests that
probed `_safe` through it had nothing left to probe - and two of them asserted a
character was *absent*, so they passed rather than failed. They go through
`receiver` now, which the `01` carries as its receiver and the `02` as its
ultimate receiver, so one junk value has to survive two records instead of one.
